# SPIKE #27: load balancing между WAN для direct-групп

Статус: **сессия 1** (дизайн + рендер + лаба L1/L2). Роутер не трогается
до вердикта; всё живёт в ветке `spike/lb`, каталог `docs/spike-lb/`.
Решения владельца (2026-10-29): отдельный тип `direct-lb`, jhash + карта
бакетов, iperf3 `-P4` для метрик L3.

## 0. Постановка (из issue #27)

Проверить на деле, не на памяти, отвергнутое в октябре 2026 решение
(ARCHITECTURE.md §7 «flows don't get faster, complexity is high»):
пер-флоу LB между WAN для direct-групп. Заимствуем **идею mwan3**
(веса + прилипание через conntrack), не пакет: официальный mwan3 —
iptables/legacy-compat, nft-порт вне фидов. Выход — вердикт
adopt/reject с доказательствами из лабы.

Границы: proxy-группа (mark 300) и wg_moscow в LB **не участвуют**;
main-таблица (mihomo-диалы, неклассифицированные) вне спайка; UDP через
TUN у proxy-группы LB не касается. UDP direct-клиентов маркируется и
LB-ится наравне с TCP (отдельного правила не нужно — см. §2).

## 1. Модель данных (UCI)

```uci
config group 'lb'
	option type 'direct-lb'
	list member_iface 'wan1'      # члены; слоты ключуются по ОТСОРТИРОВАННОМУ имени
	list member_iface 'wan2'
	option weight_wan1 '70'       # weight_<iface>; нет опции или 0/мусор -> 50
	option weight_wan2 '30'
	list member_live 'wan1'       # tick-owned (сессия 2), эффективный iface слота
	list member_live 'wan2'
config member 'm_xxx'             # члены-клиенты как у обычных групп
	option mac 'aa:bb:cc:dd:ee:55'
	option group 'lb'
```

- **Слоты по отсортированному имени члена** (не по порядку списка):
  marks/таблицы/приоритеты члена **стабильны** при смене весов и любых
  перерендерах — установленные потоки не переезжают. Пере-ключение слота
  происходит только при изменении СОСТАВА членов (добавление/удаление —
  осознанная реструктуризация, класс #24-flush).
- Веса нормализуются в бакеты mod 100: `bucket_i = floor(100*w_i/sum)`,
  остаток — последнему (70/30 → 70/30; 33/33/33 → 33/33/34). mod 100
  фиксирован (не настраивается — гранулярность 1% достаточна).
- `member_live[i]` = куда слот ездит СЕЙЧАС (пишет tick, сессия 2):
  смерть члена → его слот наследует первый живой член,apply
  перерендеривает таблицу слота (`default dev <живой>`), рендер-карта
  исключает мёртвого (его бакеты делят живые), #24-flush чистит NAT
  умершего egress. Установленные потоки мёртвого члена выживают БЕЗ
  flush'а: ct-mark ведёт их в слот мёртвого, слот едет через живого.

## 2. Рендер nft

Скелет `router/wanguard.nft` НЕ меняется: chain `marking` (prerouting
filter prio −150) достаточен. На LB-группу — 1+N правил (теги
`wg:<g>:…`, дифф существующим механизмом, без flush-окон):

```
# прилипание: установленный поток следует ct-mark и выходит из цепочки
iifname "br-lan" ether saddr @mac_lb ip daddr != @local_v4 ip daddr != @no_mark \
    ct mark != 0 counter meta mark set ct mark return
  tag: wg:lb:stick   (тело НИКОГДА не меняется — позиция в цепочке стабильна)

# новый поток: каскад numgen-random (подход mwan3: statistic random на NEW
# + connmark restore); правило i забирает долю < cut_i от ОСТАТКА.
# КАЖДОЕ member-правило ЗАКАНЧИВАЕТСЯ return — без вердикта пакет
# проваливается в следующее правило (см. находку ниже)
iifname "br-lan" ether saddr @mac_lb ip daddr != @local_v4 ip daddr != @no_mark \
    numgen random mod 100 < 70 counter meta mark set <M1> ct mark set meta mark return
  tag: wg:lb:s70@<M1>
iifname "br-lan" ether saddr @mac_lb ip daddr != @local_v4 ip daddr != @no_mark \
    counter meta mark set <M2> ct mark set meta mark return
  tag: wg:lb:s100@<M2>   (последний член — безусловный остаток, без draw)
```

- **Почему numgen random, а не jhash** (ОТКЛОНЕНИЕ от изначального
  выбора владельца, задокументировано): jhash на этом стеке
  неремонтопригоден. Живая находка сессии 1 (nft 1.1.6 + ядро 25.12):
  входные регистры конкатенации jhash портятся ЛЮБЫМ предшествующим
  выражением в правиле (set-lookup, iifname, meta mark match) И
  выражениями предыдущих правил traversal'а (голый jhash в
  jump-подцепи всё равно читает мусор). Проявления: анонимная
  интервальная карта деградирует в первый бакет, нормализованная форма
  диапазона `mod 100 0-69` не матчует никогда, реляционная форма с
  гейтом всегда даёт бакет 0. Голый jhash без префикса честен — но
  тогда правило не может отобрать клиентов группы. numgen берёт число
  из prandom, а не из регистров пакета — с полным префиксом работает
  честно (близко к 70/30 наблюдено в лабе). Именно random +
  connmark — родная схема mwan3. Утверждения L2 построены на исходе
  (успех ⟺ метка), а не на конкретном бакете — рандомность приемлема.
- Каскад: правило i = `numgen random mod 100 < cut_i` от остатка;
  независимые draws безопасны, потому что правило срабатывает только на
  недобранную долю; последний член — безусловный остаток (заодно
  обходит отказ nft на `< 100`: «Value 100 exceeds valid range 0-99»).
- **Member-правило без вердикта = каскад не каскад** (живая находка
  сессии 2, корень «блокера» сессии 1): правило без `return` не
  останавливает traversal — пакет после срабатывания rule₁ проваливался
  в безусловный rule₂, и тот перезаписывал mark. Итог: 100% потоков
  уходили последнему члену — «numgen random неравномерен (6/6 в один
  бакет)» из заметок сессии 1 был ЭТИМ багом рендера, а не draw'ом.
  Доказательство из лабы: rule₁ насчитал 29 первых SYN из 40 (72.5% ≈
  честные 70%), а conntrack показывал 39/39 mark=400. После фикса
  (return на каждом member-правиле): 40 потоков → 25×200/15×400
  (62.5/37.5 — биномиальный шум вокруг 70/30), биекция исход↔метка
  идеальная, L2 зелёная полностью (A: 11 succ/4 hang, B: 8/7; 10
  riders пережили смену весов в полёте, stick-counter 592→14948;
  post-flip remap наблюдён). Кандидаты-замены механизма (statistic
  random, numgen inc, изолированный jhash) НЕ ПОНАДОБИЛИСЬ —
  numgen random остаётся, владелец подтвердил отзыв jhash (2026-10-29).
- **Каскад — порядок-чувствительная структура, тег-дифф её ронял**
  (вторая живая находка сессии 2): reconcile добавляет новые правила
  голым `add rule`, а он APPEND'ит в КОНЕЦ цепочки. Для direct/proxy это
  всегда было безопасно (их правила дискретны по MAC-сетам, порядок не
  важен), но замена ОДНОГО member-правила (смена веса в L2) ставила
  draw-правило ПОСЛЕ безусловного остатка → все потоки сливались в
  последнего члена (лаба: 60/60 draw'ов mark=400, draw-правило 0
  пакетов). Фикс: если у группы меняется хоть один member-тег,
  перерендеривается ВЕСЬ каскад группы (append member-правил в порядке
  слотов восстанавливает порядок; stick не двигается — его тег/тело
  константны). L1 усилен порядок-проверками хэндлов: stick < draw <
  remainder при первом рендере И после смены весов (раньше L1 проверял
  только stick < «первый найденный member» — сломанный порядок
  проходил). Поведенческое подтверждение после фикса: 60 потоков →
  draw=47 / remainder=13 (78/22, шум вокруг 70/30), ok=47/hang=13 —
  биекция исход↔счётчик точная; L2 зелёная полностью (A: 10/5,
  B: 9/6; 9/9 riders через flip, stick 849→10352).
- Первый пакет (SYN) получает mark ДО fw4-MSS-clamp — конфликтов нет;
  ретранслированный SYN после confirm уже прилипает через stick.
- `counter` на всех правилах — наблюдаемость спайка (распределение и
  цена реставрации читаются прямо из nft).
- `return` из base chain = policy accept → пакет идёт дальше (redir-цепочка
  пуста для direct, затем роутинг). Стейтменты внутри правила слева
  направо: `meta mark set` ДО `ct mark set` — канонический connmark-идиом.
- Тег кодирует границу каскада и метку члена — «тег полностью
  определяет тело» (инвариант диффа #13): смена веса меняет тег →
  tag-diff заменяет правило; не тронутые веса правила не двигаются.
- Ответные пакеты (WAN→LAN) правила не матчат (`iifname "br-lan"`) —
  de-NAT по conntrack, policy-routing не нужен.
- ARP не матчится (нет ip saddr). LOCAL_V4/no_mark исключения — как у
  всех групп (правило №3 из PLAN); лаба живёт на TEST-NET-адресах
  (203.0.113/198.51.100/192.0.2 + 198.18 для LAN) именно потому, что
  172.30.x попадал в local_v4 и правила не матчили ничего (живая
  находка сессии 1).

## 3. Аллокация

`alloc_entries()` разворачивает direct-lb в N слотов, по одному на члена
(после proxy- и direct-групп; каждый слот = один шаг k обычного
аллокатора):

| группа | mark | table | prio |
|---|---|---|---|
| a (direct, wan3) | 100 | 400 | 8100 |
| lb: wan1 | 200 | 401 | 8101 |
| lb: wan2 | 400 | 402 | 8102 |

**Никаких изменений** в `reconcile_rules`/`reconcile_routes`: слот это
та же запись (mark→table, prio), таблица слота = `default dev <device
члена>` + запасной `metric 200`; сирот-чистка (правила 8000–8199,
таблицы 400–500) работает как была. Ошибся — и вся механика #13/#6/#24
переиспользована бесплатно.

## 4. Прилипание и отработка отказов (модель)

- **Прилипание = пин к СЛОТУ** (к метке), не к интерфейсу. Пока член
  жив, его слот едет на его интерфейсе: перерендеры весов/конфига поток
  не двигают (§1). Умирает член — слот (включая все прилипшие потоки)
  переезжает на живого члена через member_live; прилипшие потоки
  переживают отказ даже до flush'а, flush (#24) дочишает NAT и даёт
  перераспределение доли на новых потоках.
- wand-tick (сессия 2, L4): wand_wans() + члены LB-групп; событие
  вида `lbover:<g>:<member>><live>`; override/wanauto-семантика на
  LB-группы не распространяется (веса — ручное решение владельца).
- QUIC/UDP: direct-клиенты шлют UDP маркированно — jhash считает
  `th dport` и для UDP, прилипание то же. (У proxy-группы UDP через TUN
  — LB его не касается, граница из issue сохранена.)

## 5. Лаба (паттерн #30)

Топология `docs/spike-ucode/lab/` + **lan-мост** (в #30 LAN-стороны не
было — тикали пробы самого роутера, LB без клиента не проверить):

```
wanA 172.30.10.0/24   wanB 172.30.20.0/24   wanC 172.30.30.0/24
   |                     |                     |
[wanguard-lab-net] — якоря (uhttpd, один docroot на всех адресах)
   |                     |                     |
[wanguard-lab] eth0 .10.2 eth1 .20.2 eth2 .30.2 + eth3 → br-lan 172.30.40.1/24
[wanguard-lab-client] eth0 .40.55, MAC aa:bb:cc:dd:ee:55, gw .40.1
```

- `br-lan` собирается в setup (eth3 в бридж) — иначе маркировка
  `iifname "br-lan"` нечестная; `ip_forward=1` + masquerade LAN→WAN в
  отдельной spike-таблице (НЕ в table inet wanguard).
- Честность путей как в #30: docker-изоляция мостов — неверная пара
  (egress, dst) = честный таймаут. Адрес якоря принадлежит своему
  мосту: поток к 172.30.10.10 через eth1 — молчаливая смерть.
- Батареи:
  - **L1 render** — apply дважды (applied→in-sync); наличие stick+hash
    правил, тегов, mac-сетов; ip rule/table по слотам (route get по
    каждой метке → eth0/eth1/eth2); смена веса = замена ТОЛЬКО hash
    правила (ip rule/table/set без движений); удаление группы = чистка
    слотов (правила/таблицы/сет) без задевания соседей.
  - **L2 stickiness** — (a) каждая новая сессия получает ct-mark своего
    бакета (conntrack -L), исход сверега: успех/таймаут wget'а совпадает
    с меткой (якорь A достижим только через eth0 и т.д.); (b) дрель:
    10 параллельных длинных докачек → смена весов 70/30→30/70
    посреди докачки → все докачиваются, ct-mark не меняется,
    counter stick-правила растёт (реставрация реально работает) —
    вероятность ложного прохода без ct-реставрации ≈ 0.3^10.
  - **L3 live LB** (сессия 2) — iperf3 -P4 параллельно через оба WAN,
    агрегат vs single-WAN; счётчики правил ≈ весам.
  - **L4 failover** (сессия 2) — wan1 down в netifd-фикстуре → member_live
    → ререндер карты + flush → докачки ушли на wan2; recovery → веса
    вернулись. 
  - **L5 edges** (сессия 2) — MTU-асимметрия (veth 1436 vs 1492, большой
    download через wan1), один член, три члена (wanC), 0 живых
    (fail-open в main, как все группы).
- Mock-стенд: для спайка роль фикстурного стенда играет L1 в контейнере
  (тот же инвариант «applied→in-sync→минимальный дифф», но на реальном
  nft/ip — сильнее мока). Отдельный mock-сьют — на этапе реализации
  (после adopt), по паттерну #13.

## 6. Метрики (что докажем, п.6 issue)

Лаба: агрегатная полоса LB vs single-WAN (iperf3 -P4), распределение
счётчиков ≈ весам, цена реставрации (counter stick-правила) —
overhead на x86 ожидаемо нулевой. Прод-польза (CGNAT-контеншен
Rostelecom) — если решим измерять, отдельное живое окно ПОСЛЕ вердикта
 adopt; «пользы нет» — тоже валидный исход спайка.
